# Parity — mineflayer internal tests (U3 mapping)

Every `describe`/`it` of mineflayer 4.39.0 `test/internalTest.js` (pinned copy:
[`docs/upstream/internalTest.js`](../upstream/internalTest.js)), mapped to the unit that owns the code it exercises
(units as in the plan / `docs/CONTRIBUTING.md`) and to the Bedrock test planned for it.

This file is a **checklist** like `U0-seed.md` (the `parity:seed` marker above): rows belong to the unit in the owner
column, which copies its rows into its own `docs/parity/U<n>.md` when it writes the test (same item text, `kind` test),
updates `status` and fills `asserting test`. `corepack pnpm parity` then takes the unit's row. U3 owns only the two
`onceWithCleanup` rows (ported verbatim below).

How the upstream tests work: each one starts a minecraft-protocol **server** in-process, lets a real bot join it and writes
Java packets at it. There is no in-process BDS, so the Bedrock analogs are **unit tests with a fake bedrock-protocol
client** (as in `test/unit/smoke.test.js` / the conformance test): inject the bot, emit Bedrock packets on the client —
recorded ones from `test/fixtures` (`fixtures.load('join_flat')`, regenerated with `scripts/capture-fixtures.js`) or
synthesized ones — and assert the same bot state/events; outbound packets are read from `client.written`. Name the
Bedrock test after the upstream one (`internalTest › <describe> › <it>`) so the row's asserting test is obvious. Where a
Java mechanism does not exist on Bedrock the analog asserts the Bedrock equivalent (`adapted`, with a differences entry)
or the documented absence (`n.a.`).

Planned test files follow `packages/mineflayer-bedrock/test/unit/<area>.test.js` (owned by the unit that creates them).
